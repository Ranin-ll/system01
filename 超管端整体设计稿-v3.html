权限边界：读全量，写收窄

边界重划

原文把超管的写操作整体封死（isGlobalReadOnly() 命中即抛异常，覆盖 6 个业务 Service）。 本次明确：超管在账号 / 通知 / 督办三域必须有写权限，而业务实例继续只读。

能力域超级管理员部门管理员落地方式
账号与组织可写 全量仅本部门实习生复用 /system/user，超管已授权（建 / 停用部门管理员、改派导师、重置密码）
通知可写 全员 / 部门 / 岗位 / 指定人员仅本部门业务表 notice（需补 scope_type='USER' 一档）
督办催办可写 任意部门管理员 / 实习生本部门新增，催办即写定向通知并留痕
报名审核可写本部门现状保留（business:register:audit 已授权）
课程 / 题库 / 考试 / 实操题只读本部门可写保持 isGlobalReadOnly()
系统配置 / 菜单 / 字典可写不可见平台原生
划

收窄后的判定

业务实例 Service（6 个）继续只读
账号 / 通知 / 督办（新增）不套用该判定
涉及的 6 个 Service：Course / CourseContent / Exam / Question / QuestionBank / PracticeSubject。
警

一处需你知晓的重复保护

超管当前持有 business:psubject:add/edit/remove 三个写权限，但 PracticeSubjectService 已被 isGlobalReadOnly() 拦住。两条保护并存不冲突，只是权限矩阵上看着"给了却没生效"——本稿不改动它。

★ 新增

为什么 A 类天然是全量：超管命中 isGlobalReadOnly() → currentScopeDeptId() 返回 null → Mapper 的部门过滤条件不生效 → SQL 直接返回所有部门的数据。不是靠前端筛选，是 SQL 层就没有 where dept_id。
C 类为什么必须新增接口：「已实现接口的注解不改」是我们的硬约束，而 learning 的注解在类级别， 无法只放行单个方法。所以在 /business/super/analysis/intern/{userId} 里统一取「学习 + 模拟 + 正式 + 评价」四段， 一次返回，绕开这两个注解。

三档作用域：全局 / 多部门横向 / 单部门

★ 本轮新增

需求里其实区分了两种视图语义：「各部门横向比对」是跨部门的，「部门内部统计」是部门内的。 两者口径不同，混在一页会出现「5 个部门混算成一个数」这类错误。所以统一成一个选择器、三档语义。

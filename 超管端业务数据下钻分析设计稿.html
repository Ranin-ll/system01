需求与层级模型

五层下钻

需求原话：「业务相关的管理，可以有所有部门集体宽泛的对比可视化统计，然后分部门下钻看各部门的统计，再下钻具体业务数据，可以多个层级页面。」三个诉求拆开是：① 跨部门的横向对比 ② 逐层下钻 ③ 多层级页面。

!
为什么用「独立路由」而不是「单页切换」

本项目刚踩过一次：消息中心的「去处理」原来拼成 /messages?biz=task&id=N，落点就是本页 → vue-router 走「同 path 只换 query」→ 组件不重建，用户看到的就是「点了没反应」。下钻场景天然要换数据源，独立路由额外拿到三个好处：URL 可分享、刷新不丢位置、浏览器前进后退可用。

五层下钻 + 一张横切矩阵面包屑由 URL 段动态生成，不做固定 5 级硬编码
超管端 · 培养运营
L0 业务总览 /super/ops/analysis 所有部门横向对比 · 唯一的作用域选择器（全局 / 多部门 / 单部门）
L1 部门详情 /super/ops/analysis/dept/103 该部门内部统计 · 岗位分布 / 课程完成率 / 成绩 / 薄弱知识点
L2 场次明细 /super/ops/analysis/exam/25 全量名单 · 分数段分布 · 理论 vs 实操环节对比
L3 个人 360 /super/ops/analysis/intern/127 学习进度 + 模拟逐题 + 正式逐题 + 阶段评价（四段一次拉齐）
L4 题目详情 /super/ops/analysis/question/{id} 正确率 · 选项分布 · 出现在哪些场次 · 谁答对谁答错
横切 知识点矩阵 /super/ops/analysis/knowledge 部门 × 知识点 热力矩阵 · 不占层级，可从任意层进入
点某部门 → L1；点某场次/课程 → L2；点某个人 → L3；点某道错题 → L4。每一层顶部的面包屑（业务总览 › 开发部门 › 开发部门模拟理论自测 › 张某）每一段都可点回。

四条分层原则为什么这么切
  • 侧栏最多两级。三级一律做成页面内的页签 / 区块，不做第三级菜单 —— 本项目侧栏是前端硬编码（buildSuperSidebar()），层级越深，维护成本和「改了没生效」的概率越高。
  • 下钻页不进侧栏。它们不是「功能」而是「某个数据对象的详情」，数量随数据增长（部门 × 场次 × 人 × 题）。只通过 URL + 面包屑到达。
  • 单项目录自动折叠。全局工作台 / 任务与通知 / 规则与配置 / 审计与合规各只有一页，侧栏里折叠成一级链接（不显示展开箭头）。
  • 路径三段固定 /super/{组}/{页}，下钻页在页后追加 /{类型}/{id}。不出现第 4 段固定菜单。

    路径规则：分组目录写「相对段」，单项目录写「绝对路由」

    侧栏拼接用的是 path.resolve(basePath, childPath)，basePath 取目录自身的 path。
    分组目录 group('/super/ops', …) 的目录路径是 /super/ops，「组路径 + 末段」正好等于真实路由 → 子项写 'ops/analysis' 即可拼成 /super/ops/analysis ✓
    单项目录 single('/super/rule', 'rule') 的目录路径本身就是真实路由 /super/rule，再拼一段会变成 /super/rule/rule → 404。所以单项目录的子项必须写绝对真实路由。
    本稿所有分析页都挂在「培养运营」组下，所以前端路由是 /super/ops/analysis 而不是 /super/analysis —— 后者是多拼/少拼一层都会 404 的写法。

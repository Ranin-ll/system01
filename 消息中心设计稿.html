设计总览：一个入口，两根管道

★ 新设计

需求里同时存在两种东西：通知（「我告诉你」）与 任务（「你要做」）。 它们语义不同、数据来源不同、处理动作也不同 —— 所以 同一页两个页签，但顶栏只给一个铃铛，避免用户要在两个地方找消息。

管

维度通知（广播）任务（待办）
语义我告诉你一件事你要做一件事
数据源notice + 送达谓词task_assignment（per-user）
可见性按范围 ALL/DEPT/POSITION/USER只有被分配的人
有无状态已读 / 未读未开始 / 进行中 / 已完成 / 逾期

页签两者并置在同一页：「通知」/「我的任务」
判别口诀：读完就结束的是通知，读完了还得做的是任务。

后端全链路（一）数据模型与送达谓词

★ 待落地

全链路的地基只有两件事：消息存哪、谁该收到。第二件如果不在 SQL 层收敛成一个谓词，未读数和列表条数必然对不上。

表

三处改动：扩展 1 张 + 新增 2 张

幂等迁移脚本
对象动作内容与理由
notice扩列 补 msg_type（ANNOUNCE/TASK/EXAM/AUDIT/URGE/SYSTEM，用于类型标签与筛选）、 biz_type + biz_id（点击去哪的锚点）、link_url（可选显式路径）、 sender_id、status（DRAFT/PUBLISHED/REVOKED）。复用它的 scope 语义，不另立 message 表
notice_target新建 (notice_id, user_id) + 唯一键。解决 scope_id 单值存不下多人 —— 催办/再提醒/批阅回执全靠它
notice_read新建 (notice_id, user_id, read_time) + 唯一键。唯一键即幂等：重复打开详情不会写两行。没有它就没有未读红点与送达统计
任务域不另建消息表：task_assignment 本身就是 per-user 的，「我的任务」直查即可，到期/逾期用 deadline 实时算。 但任务的事件（发布 / 批阅 / 逾期）必须落 notice，否则不会出现在「通知」页签里。
谓

送达谓词（全链路的唯一口径，三端共用）

建议抽成 Mapper 复用
-- 谁该收到（可复用于 列表 / 未读数 / 送达数，改一处全局生效）
       n.status = 'PUBLISHED'
  AND (n.effective_to IS NULL OR n.effective_to > NOW())
  AND (
        (n.scope_type = 'ALL'      AND u.status = '0' AND u.del_flag = '0')
     OR (n.scope_type = 'DEPT'     AND u.dept_id     = n.scope_id)
     OR (n.scope_type = 'POSITION' AND u.position_id = n.scope_id)
     OR (n.scope_type = 'USER'     AND EXISTS (SELECT 1 FROM notice_target t
                                                WHERE t.notice_id = n.id AND t.user_id = u.user_id))
      )

-- 未读数：命中谓词 − 已读（一次查完，不做 N+1）
SELECT COUNT(*) FROM notice n
  LEFT JOIN notice_read r ON r.notice_id = n.id AND r.user_id = #{userId}
 WHERE <上面的谓词> AND r.id IS NULL

-- 发送方的送达/已读统计
SELECT (SELECT COUNT(*) FROM 命中谓词集合) AS delivered,
       (SELECT COUNT(*) FROM notice_read WHERE notice_id = #{id}) AS readCount
为什么必须收敛：铃铛未读数、消息列表、发送方的送达统计、实习生工作台的「未读消息」KPI —— 这四处只要各写各的 SQL，迟早出现 「铃铛显示 3、列表只有 2」这类对不上的 bug。收发两端共用同一张 notice_read，也天然避免「这边已读、那边还红着」。
